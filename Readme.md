# incus-metadata-service

A cloud-init compatible metadata service for [Incus](https://linuxcontainers.org/incus/), providing instance metadata, user data, network configuration, and vendor data to VMs and containers at boot time.

## Overview

Incus does not ship a native instance metadata service equivalent to AWS IMDS or GCP's metadata server. When a VM or container boots and runs `cloud-init`, it needs an HTTP endpoint to fetch its metadata, user data, and network configuration. This service fills that gap.

It connects to an Incus server over its API, synchronises instance state into a local SQLite database, and then serves cloud-init compatible endpoints. Instances are identified by their source IP address, so no special configuration inside the guest is required beyond pointing `cloud-init` at the service address.

The service supports optional multi-node high availability through RAFT consensus, making it suitable for production Incus clusters.

## Features

- Cloud-init compatible endpoints (`/configs/meta-data`, `/configs/user-data`, `/configs/network-config`, `/configs/vendor-data`)
- IP-based instance identification — no agent or guest configuration required
- Event-driven synchronisation with the Incus server using its event API
- Periodic cron-based reconciliation to keep instance state consistent
- RAFT consensus (via `hashicorp/raft`) for high-availability multi-node deployments
- SQLite storage with type-safe queries generated by [SQLC](https://sqlc.dev/)
- Content negotiation — endpoints return JSON or YAML based on the `Accept` header
- Structured logging via [zerolog](https://github.com/rs/zerolog)

## Architecture

The service is composed of four internal layers:

- **api** — Gin HTTP router with two route groups: public `/configs/*` endpoints consumed by cloud-init inside guests, and internal `/internal/*` endpoints for managing vendor data. A `/health` and optional `/raft/status` endpoint are also registered.
- **events** — An event manager that subscribes to the Incus event stream to react to instance lifecycle changes in real time, and a cron manager that periodically reconciles instance state against the Incus API.
- **consensus** — A RAFT node built on `hashicorp/raft` with BoltDB as the log store. When enabled, writes are proposed through the cluster leader and applied to all nodes via a finite state machine backed by the SQLite database.
- **storage** — SQLite database accessed through SQLC-generated type-safe queries. The schema stores instances, instance state, metadata, user data, network configuration, vendor data, and instance logs.

```
┌─────────────────────────────────────────────────┐
│                   HTTP (Gin)                    │
│  /configs/*  │  /internal/*  │  /health  │  /raft │
└────────────────────┬────────────────────────────┘
                     │
          ┌──────────┴──────────┐
          │       events        │  <- Incus event stream + cron
          └──────────┬──────────┘
                     │
          ┌──────────┴──────────┐
          │     consensus       │  <- RAFT (optional)
          └──────────┬──────────┘
                     │
          ┌──────────┴──────────┐
          │  storage (SQLite)   │
          └─────────────────────┘
```

## Prerequisites

- Go 1.24 or later
- A running Incus server with API access enabled
- TLS client certificate and key for authenticating with the Incus API (see [Incus authentication docs](https://linuxcontainers.org/incus/docs/main/authentication/))
- [SQLC](https://sqlc.dev/) (only required to regenerate queries after schema changes)

## Configuration

All configuration is read from environment variables. The service uses `sethvargo/go-envconfig` and will fail fast on startup if a required value is missing.

### Service

| Variable    | Default  | Description                                        |
|-------------|----------|----------------------------------------------------|
| `PORT`      | `8080`   | Port the HTTP server listens on                    |
| `LOG_LEVEL` | `info`   | Log level: `debug`, `info`, `warn`, or `error`     |

### Incus

All variables are prefixed with `INCUS_CONFIG_`.

| Variable                                  | Default                  | Description                                                  |
|-------------------------------------------|--------------------------|--------------------------------------------------------------|
| `INCUS_CONFIG_SERVER_URL`                 | `https://localhost:8443` | URL of the Incus server API                                  |
| `INCUS_CONFIG_TLS_CLIENT_CERT`            | `/etc/incus/client.crt`  | Path to the TLS client certificate                           |
| `INCUS_CONFIG_TLS_CLIENT_KEY`             | `/etc/incus/client.key`  | Path to the TLS client private key                           |
| `INCUS_CONFIG_TLS_SERVER_CERT`            | *(empty)*                | Path to the Incus server certificate for pinning (optional)  |
| `INCUS_CONFIG_TLS_INSECURE_SKIP_VERIFY`   | `false`                  | Skip TLS verification (for self-signed certs in development) |

### Database

All variables are prefixed with `DATABASE_CONFIG_`.

| Variable                    | Default       | Description                                         |
|-----------------------------|---------------|-----------------------------------------------------|
| `DATABASE_CONFIG_DB_DRIVER` | `sqlite`      | Database driver                                     |
| `DATABASE_CONFIG_DB_SOURCE` | `metadata.db` | SQLite file path (or DSN for other drivers)         |

### RAFT

All variables are prefixed with `RAFT_`. RAFT is disabled by default; the service runs as a standalone node.

| Variable         | Default          | Description                                                             |
|------------------|------------------|-------------------------------------------------------------------------|
| `RAFT_ENABLED`   | `false`          | Enable RAFT consensus mode                                              |
| `RAFT_NODE_ID`   | `node1`          | Unique identifier for this node in the cluster                          |
| `RAFT_BIND_ADDR` | `localhost:7000` | TCP address for RAFT inter-node communication                           |
| `RAFT_DATA_DIR`  | `raft-data`      | Directory for RAFT log and snapshot storage                             |
| `RAFT_PEERS`     | *(empty)*        | Comma-separated peer addresses, e.g. `host2:7000,host3:7000`           |
| `RAFT_BOOTSTRAP` | `false`          | Bootstrap a new cluster from this node (set once on first startup only) |

## Running

### Single node (default)

```bash
go run ./metadata-service/cmd/server/main.go
```

Override defaults as needed:

```bash
PORT=9090 \
  INCUS_CONFIG_SERVER_URL=https://10.0.0.1:8443 \
  INCUS_CONFIG_TLS_CLIENT_CERT=/home/user/.config/incus/client.crt \
  INCUS_CONFIG_TLS_CLIENT_KEY=/home/user/.config/incus/client.key \
  go run ./metadata-service/cmd/server/main.go
```

### Multi-node RAFT cluster (3 nodes)

Start each node in a separate terminal. Set `RAFT_BOOTSTRAP=true` only on the node that initialises the cluster, and only on the very first startup.

**Node 1 (bootstrap leader):**

```bash
RAFT_ENABLED=true \
  RAFT_NODE_ID=node1 \
  RAFT_BIND_ADDR=localhost:7000 \
  RAFT_DATA_DIR=/tmp/raft-node1 \
  RAFT_PEERS=localhost:7001,localhost:7002 \
  RAFT_BOOTSTRAP=true \
  PORT=8081 \
  DATABASE_CONFIG_DB_SOURCE=/tmp/node1.db \
  go run ./metadata-service/cmd/server/main.go
```

**Node 2:**

```bash
RAFT_ENABLED=true \
  RAFT_NODE_ID=node2 \
  RAFT_BIND_ADDR=localhost:7001 \
  RAFT_DATA_DIR=/tmp/raft-node2 \
  RAFT_PEERS=localhost:7000,localhost:7002 \
  RAFT_BOOTSTRAP=false \
  PORT=8082 \
  DATABASE_CONFIG_DB_SOURCE=/tmp/node2.db \
  go run ./metadata-service/cmd/server/main.go
```

**Node 3:**

```bash
RAFT_ENABLED=true \
  RAFT_NODE_ID=node3 \
  RAFT_BIND_ADDR=localhost:7002 \
  RAFT_DATA_DIR=/tmp/raft-node3 \
  RAFT_PEERS=localhost:7000,localhost:7001 \
  RAFT_BOOTSTRAP=false \
  PORT=8083 \
  DATABASE_CONFIG_DB_SOURCE=/tmp/node3.db \
  go run ./metadata-service/cmd/server/main.go
```

## API Reference

All public endpoints (`/configs/*`) are intended to be called from inside a guest instance. The requesting instance is identified by its source IP address — no authentication is required from the guest.

Internal endpoints (`/internal/*`) are for administrative use and should not be exposed to guests.

### Public — cloud-init endpoints

| Method | Path                      | Description                                               | Content types              |
|--------|---------------------------|-----------------------------------------------------------|----------------------------|
| `GET`  | `/configs/meta-data`      | All metadata for the calling instance                     | `application/json`, YAML   |
| `GET`  | `/configs/meta-data/:key` | A single metadata field by key                            | `application/json`, YAML   |
| `GET`  | `/configs/user-data`      | Cloud-init user data (raw YAML or shell script)           | `text/yaml`                |
| `GET`  | `/configs/vendor-data`    | Vendor data for the default vendor entry                  | `application/json`         |
| `GET`  | `/configs/network-config` | Cloud-init network configuration for the calling instance | YAML                       |

Content negotiation for metadata endpoints is driven by the `Accept` request header. Supported values are `application/json` and `application/yaml` (or `text/yaml`). An unsupported `Accept` value returns `406 Not Acceptable`.

### Internal — vendor data management

| Method | Path                                 | Description                   | Content type       |
|--------|--------------------------------------|-------------------------------|--------------------|
| `POST` | `/internal/vendor`                   | Create a new vendor data entry | `application/json` |
| `GET`  | `/internal/vendor/:vendor_name/data` | Retrieve vendor data by name  | `application/json` |
| `PUT`  | `/internal/vendor/:vendor_name/data` | Update vendor data by name    | `application/json` |

**Create vendor data — request body:**

```json
{
  "vendor_name": "my-vendor",
  "description": "optional description",
  "data": {
    "key": "value"
  }
}
```

**Update vendor data — request body:**

```json
{
  "data": {
    "key": "new-value"
  }
}
```

### Health and cluster

| Method | Path           | Description                                             | Notes                          |
|--------|----------------|---------------------------------------------------------|--------------------------------|
| `GET`  | `/health`      | Returns `200 OK` when the service is running            | Always available               |
| `GET`  | `/raft/status` | Returns RAFT node state, leadership, and leader address | Only available when RAFT is enabled |

**RAFT status response:**

```json
{
  "is_leader": true,
  "leader_addr": "localhost:7000",
  "state": "Leader"
}
```

## Development

### Build

```bash
go build -o bin/metadata-service ./metadata-service/cmd/server/main.go
```

### Test

```bash
go test ./...
```

### Regenerate SQLC queries

After modifying `metadata-service/internal/storage/db/schema.sql` or any `.sql` query files, regenerate the Go code:

```bash
sqlc generate
```

Requires `sqlc` to be installed. See the [SQLC installation guide](https://docs.sqlc.dev/en/latest/overview/install.html).

```bash
gofmt -w ./...
```
